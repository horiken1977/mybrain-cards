# mybrain-cards 設計書

読書（Kindleハイライト）を「AIが探せる状態」で終わらせず「自分の頭から取り出せる状態」まで持っていくための、間隔反復＋想起テストの仕組み。mybrain本体（`raw/`・`wiki/`）とは別の独立リポジトリとして運用する。

設計の出発点は mybrain側の `wiki/analysis/kindle-reading-retention-design.md`（Qiita「気合ではなくログで管理する学習法」を参考にした最初の設計）。本ドキュメントはその後スマホ運用化のために変更した実装の設計を記す。

---

## 0. バージョン状況

| | 状態 | 回答の場所 | 採点 | 結果の閲覧 |
|---|---|---|---|---|
| **v1**（§1〜11、現行実装） | 実装済み・動作確認済み（2026-09-30） | GitHub Issueのコメント | Issueコメント作成をトリガーにGitHub Actions＋Claude API | Issueのコメント欄 |

v1は「Webサイトで問題を読む→Issueに移動して回答する」という導線がユーザー体験として良くないという指摘（2026-09-30）を受け、v2ではサイト内で完結させる設計に変更する。**v2の実装はまだ行っていない**（本ドキュメントは設計のみ）。v1は当面そのまま動作する。

## 1. 目的

- ingest（mybrain側）は「AIが要約して検索できる状態」を作るだけで、人間の記憶には効かない
- カードは「AIを出題係にして、本人に思い出させる／自分の言葉で言わせる」ことで定着させる
- 毎日欠かさず回答できるよう、Mac起動に依存しないスマホ運用を主軸にする

## 4. データモデル（カード）

```yaml
---
title: カードタイトル（アイデアの一言）
type: card
book: "[[entities/書籍エンティティ名]]"   # mybrain側のentityへのwikilink文字列
status: 未履修          # 未履修 / 要復習 / 学習中 / 要確認 / 安定
priority: 中            # 高 / 中 / 低
last_reviewed:          # YYYY-MM-DD（未実施なら空）
next_review: YYYY-MM-DD
streak: 0               # 前回と別の日・別の型の問いに連続合格した回数
tags: []
---

## 主張        # 自分の言葉で1文（初回は/recallで自分の言葉に直す）
## 根拠        # ハイライト原文＋Kindle locationリンク＋自分のメモ＋原本パス
## なぜ自分に重要か   # 本人が1行（AIは代筆しない）
## 使う場面     # 「〇〇のとき、これを使う」
## 回答履歴     # - 日付 | 型 | 点数 | 合否 | 一言フィードバック
```

新規カードが未記入（「なぜ自分に重要か」等に `（未記入：…）` が残っている）の間は、出題ロジックが最優先で「補完（fill）」の問いにする。

## 5. 出題ロジック（`lib.select_cards`）

1. **未記入カードがあれば最優先**（最大3枚、記入させるだけで採点なし）
2. 無ければ `next_review <= 今日` または `status: 未履修` の「期限到来カード」を対象に：
   - `priority`（高→中→低）
   - 期限超過日数が長い順
   - 異なる本が混ざるよう選ぶ（同じ本ばかりにしない）
3. 上限3枚

### 問いの型（`streak` で決まる）

| streak | 型 | 問い方 |
|---|---|---|
| 0 | 想起 | 本を見ずに自分の言葉で説明 |
| 1 | 適用 | 今週の実際の場面でどう使うか |
| 2 | 対比・接続 | 別カードの主張とどこで対立・補完するか |
| 3 | 反証 | 成り立たない場面は何か |
| 4以上 | ローテーション | 上記を回す |

### 採点（Claude API、`grade_and_update.grade_with_claude`）

4軸（主張の正確さ／自分の具体例／適用条件と限界／次の行動）を各0〜2点。**合計5点以上かつ主張の正確さ1点以上で合格**。

### 状態更新

| 結果 | 更新 |
|---|---|
| 合格（前回と別の日・別の型） | `streak`+1、状態を1段階進める |
| 合格（同日・同型の再挑戦） | 状態は進めない |
| 不合格 | 状態を1段階戻す、`streak`-1（下限0）、`next_review`は翌日 |

次回確認日（合格時）：要復習=1日 → 学習中=3日 → 要確認=7日 → 安定=30日（安定で合格継続なら60日）。

## 6. Issue⇄カードの対応づけ

Issue本文に、各設問ブロックの直前へ隠しメタデータを埋め込む（Markdownでは非表示、レンダリング後も見えない）：

```
<!-- recall-meta: {"card": "<ファイル名>.md", "qtype": "fill|recall|apply|contrast|refute"} -->
```

回答コメントは `A1.` `A2.` `A3.` の見出しでパースし（設問が1件のときだけ番号省略を許容）、Issue本文から拾ったメタデータと突き合わせて対象カードを特定する。

## 7. GitHub Pages ページ

- `docs/index.html` を出題のたびに**上書き**生成（日付ごとの履歴は残さない、常に「今日」だけを表示）
- 内容：各設問の見出し・引用・問いの説明（Issueと同じ情報をHTML装飾したもの）
- 末尾に「回答する」ボタン（その日作成したIssueへの直リンク）
- 回答フォーム自体は持たない（静的サイトのため）。回答は必ずGitHub Issueのコメントで行う
- メール本文の先頭にこのページのURLを置くことで、GitHubのIssue通知メールがそのまま「読みやすいページへの入口」になる（専用の送信サービスは使っていない＝GitHub標準の通知機能に相乗り）

## 8. Mac側との同期

`/card`・`/recall`（mybrain側 `.claude/commands/`）は、`cards/` が独立git repoであることを前提に：

- 実行前に `git pull`
- 完了後に `git add -A && git commit && git push`

同一カードをMacとスマホで同日に編集すると衝突しうるため、基本はスマホの日次フローに任せ、Macは新規カード作成（`/card`）や重い振り返りに使う想定。

## 9. セキュリティ・プライバシー

- **2026-09-29**：`cards/` をmybrain本体（`raw/`の個人情報・キャリア情報等）から切り離した独立repoにする方針を決定（Git自体はセキュリティ上の懸念で一旦見送っていたが、cards専用の小さいリポジトリに限定する形で復活）
- **2026-09-30**：GitHub PagesがFreeプランではprivate repoに使えないため、`horiken1977/mybrain-cards` を**public**に変更。読書ハイライト（本の引用）と自分の振り返り（「なぜ重要か」「使う場面」）がインターネット上に公開される点は把握した上での判断
- 採点のため、回答テキストと該当カードの主張・根拠がClaude API（Anthropic）に送信される。コストは`claude-haiku-4-5`使用で月数十〜数百円の想定
- mybrain本体（raw/の生資料・career/finance等）はこのリポジトリに一切含まれない

## 10. 運用時に判明した既知の課題（2026-09-30のテストから）

1. **同名Issueの取り違え**：テストで同日に複数Issue（同じタイトル）を作ったため、メール通知のスレッドを間違えて古い（close済みの）Issueに返信する事故が複数回発生した。実運用では1日1Issueのみのため再現しにくいが、メール返信ではなくPagesページ経由でその都度正しいIssueへ遷移する導線（本設計の§7）で軽減している
2. **番号なし回答の誤割当てバグ（修正済み）**：設問が複数あるIssueで `A1.` 等の番号を付けない回答を「質問1への回答」と誤解釈し、無関係なカードを上書きする不具合があった。→ 設問が2件以上のときは番号必須とし、パースできない場合は**カードを更新せず**再送を促す方式に修正（`grade_and_update.parse_answers` / `handle_fill`）
3. **GitHub Pages is Free プランではprivate repo非対応**：事前に把握しておらず、実装後に判明した。§9の通りpublic化で対応

## 12. 次期設計（v2）— サイト内で回答・採点・結果表示を完結させる（設計のみ・未実装）

### 12.1 動機

v1は「GitHub Pagesで問題を読む → 回答のためだけにGitHub Issueへ移動する」という2段構えで、実際の運用テスト（2026-09-30）でも「どのIssueに返信すべきか迷う」「メール返信の引用がうまく切り出せない」といったUX上の事故が繰り返し起きた。v2では**回答・採点・結果表示のすべてをWebサイト（同じページ）内で完結**させ、Issueへの移動自体をなくす。

### 12.2 なぜGitHub Issuesを使わずに済むか

GitHub Pagesは静的サイトのため、それ単体ではフォーム送信を受け取れない。v1はその制約を「Issueコメント」で回避していたが、v2では**サーバーレス関数**を1つ挟むことで、静的サイトのまま回答受付・採点・結果保存までを行う。

### 12.3 アーキテクチャ

```
┌──────────────────────────────────────────────────────────────┐
│ 毎朝08:00 JST（GitHub Actions, 既存の daily-question.yml を流用）│
│  1. 出題カードを選ぶ（lib.select_cards、変更なし）               │
│  2. docs/index.html を生成（フォーム付き。Issueは作らない）       │
│  3. docs/today.json を生成（カードID・問いの型・問い文を格納）     │
│  4. git push（docs/）→ GitHub Pagesに反映                       │
└───────────────────────────┬──────────────────────────────────┘
                             │ 通知メール（本文はPagesリンクのみ）
                             ▼
                    スマホでメールを開き、Pagesのリンクをタップ
                             │
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ GitHub Pages（docs/index.html）                                │
│  - today.json を読み込み、問いと回答欄（<textarea>）を表示        │
│  - 送信ボタン押下 → fetch() で下記Workerへ POST                 │
│  - Workerからのレスポンス（点数・フィードバック）をその場に表示     │
└───────────────────────────┬──────────────────────────────────┘
                             │ POST /grade { card, qtype, answer }
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ サーバーレス関数（推奨: Cloudflare Workers、無料枠で十分）        │
│  1. Claude API（claude-haiku-4-5）に採点を依頼                  │
│  2. GitHub Contents API で該当カードファイルを更新（commit）      │
│  3. 採点結果（点数・フィードバック・新status）をJSONで返す         │
└──────────────────────────────────────────────────────────────┘
```

### 12.4 画面設計

v2は複数ページのサイトではなく、**1枚のページ（`docs/index.html`）の中で、設問ごとに独立した「問いカード」がそれぞれ状態を持つ**構成にする（v1の静的カード表示をそのままインタラクティブにしたもの）。ページ全体のナビゲーションや画面遷移は発生しない。

#### ワイヤーフレーム（スマホ幅・設問2件の例）

```
┌───────────────────────────────┐
│  想起テスト                     │
│  2026-09-30                    │
├───────────────────────────────┤
│ Q1  会議は場で完結させる          │  ← 問いカード（状態: pending）
│    （世界一流エンジニアの思考法）  │

│  └───────────────────────────┘ │
│                                 │
│        [ 回答する ]              │
├───────────────────────────────┤
│ Q2  危機感がない病：…             │  ← 別カード。Q1とは独立
│    （V字回復の経営） 未確定       │
```

補完（fill）タイプは、v1では「a)/b)/c)を1つのテキストに書いてもらい正規表現で分割」していたが、v2はフォームなので**最初から3つの入力欄を分ける**。これによりv1の「3点に分割できず記入を拒否する」というエラー処理自体が丸ごと不要になる。

#### 問いカードの状態遷移

```
pending（未回答・入力可）
   │ 回答を入力して送信ボタン押下
   ▼
submitting（送信中・ボタン無効化＋スピナー表示、入力内容は保持）
   │                         │
   │ 成功                     │ 失敗（通信エラー／採点API失敗など）
   ▼                         ▼
result                    error
（点数・可否・            （エラー文言＋「再送信」ボタン。
 フィードバック表示。       入力していた回答は消さない）
 fillタイプは              │
 「記入ありがとう           │ 再送信ボタン押下
 ございます」のみ）          └──────────▶ submitting へ戻る
```

- `result` に達したカードは入力欄を読み取り専用にし、点数と一言フィードバックを表示する（再送信はしない。誤答の再挑戦は翌日以降の通常の出題サイクルに任せる＝現行の状態遷移ルールと同じ）
- 全カードが `result` になったら、ページ最上部に「今日の3問はすべて回答済みです」のような完了メッセージを出す
- ページを閉じて後から同じURLを開き直した場合、`docs/today.json` 自体は変わらない（同じ日はずっと同じ内容）ため、**どのカードが回答済みかをブラウザ側で覚えておく必要がある**（→ 12.6 でlocalStorageの扱いを定義）

### 12.5 データの流れ（詳細シーケンス）

```
[1] ページ読み込み
    ブラウザ ─ GET docs/today.json ──▶ GitHub Pages（静的ファイル）
    ブラウザ ← today.jsonの内容 ─────┘
    ブラウザのJSが localStorage を見て、今日すでに回答済みのcardは
    result表示（過去に返ってきた点数・フィードバックをlocalStorageに
    保存しておいたものを再表示）にする

[2] 回答送信（未回答のカードのみ）
    ブラウザ ─ POST https://<worker>.workers.dev/grade ──▶ Worker
              Body: {date, card, qtype, answers}
              （fillタイプは answers が {claim, why, scene} の3フィールド、
               それ以外は answers が {text} の1フィールド）

[3] Worker内の処理
    a. リクエストのバリデーション（必須フィールド・日付形式など）
    b. GitHub Contents API
       GET /repos/horiken1977/mybrain-cards/contents/{card}?ref=main
       → { content(base64), sha }
    c. base64をデコードしてfrontmatter/本文をパース（lib.pyと同じ規則をJSに移植）
    d. qtype=fill の場合：主張／なぜ自分に重要か／使う場面 の該当箇所を
       answers.claim / answers.why / answers.scene で置き換え
       qtype!=fill の場合：Anthropic Messages API を呼び、4軸採点＋feedbackを取得
    e. frontmatter（status/streak/last_reviewed/next_review）と
       回答履歴 を更新した新しい本文を組み立てる
    f. GitHub Contents API
       PUT /repos/horiken1977/mybrain-cards/contents/{card}
       Body: {message, content(base64・更新後), sha(bと同じ値), branch: "main"}
       → 新しいコミットとしてカードファイルが更新される

[4] レスポンス
    Worker ─ JSON ──▶ ブラウザ
    ブラウザは受け取ったJSONでそのカードのUIを result 状態に更新し、
    同じ内容を localStorage にも保存する（次回読み込み用）
```

### 12.6 データの格納方法

#### `docs/today.json`（daily-question.ymlが毎日生成・上書き）

```json
{
  "date": "2026-09-30",
  "questions": [
    {
      "card": "会議は場で完結させる.md",
      "qtype": "apply",
      "title": "会議は場で完結させる",
      "book": "世界一流エンジニアの思考法",
      "text": "今週の実際の場面を1つ挙げ、この考えをどう使うか説明してください。",
      "fields": ["text"]
    },
    {
      "card": "危機感がない病：業績と自分が紐づいていない.md",
      "qtype": "fill",
      "title": "危機感がない病：業績と自分が紐づいていない",
      "book": "V字回復の経営",
      "claim_draft": "大赤字でも危機感が生まれないのは、自分の仕事・給与・評価が業績と紐づいていないから。",
      "fields": ["claim", "why", "scene"]
    }
  ]
}
```

- `fields` は、その問いカードに何個・どんな入力欄を出すかをJS側に明示するためのフィールド（`text`＝1個の自由記述欄、`["claim","why","scene"]`＝fillタイプの3欄）
- 1日1ファイルで上書き。過去日のログは持たない（v1と同じ方針。履歴が要る場合は各カードの`回答履歴`を見る）

#### POSTリクエストのペイロード（ブラウザ→Worker）


#### カードファイル本体（GitHubリポジトリ、Contents API経由で更新）

- 保存形式・frontmatterのスキーマはv1と同一（CLAUDE.md「定着レイヤー」参照）。**v2で変わるのは更新経路だけ**（GitHub Actions経由 → Workerの直接API呼び出し）
- 1回の回答につき1コミット（v1の`grade-response.yml`と同じ粒度）。コミットメッセージ例：`recall(web): update card state for 2026-09-30`、コミッターは専用のBot名義（例: `recall-worker <actions@users.noreply.github.com>`。GitHub Contents APIの`author`/`committer`フィールドで指定）
- パスに日本語・記号（`：`）を含むため、Contents APIを叩く際は各パスセグメントを`encodeURIComponent`する
- 同時更新の衝突（同じファイルへの並行PUT）はGitHubが`sha`不一致で409を返すので、Workerは1回だけ再取得→再試行する

#### ブラウザ側の一時状態（localStorage）

- キー例：`recall:2026-09-30:会議は場で完結させる.md`
- 値：Workerからのレスポンス全体（JSON文字列）
- 用途：同じ日にページを再読み込みしても「回答済み」の表示を復元するためだけの**キャッシュ**。消えてもカード本体（GitHubリポジトリ側）のデータには影響しない＝正本はあくまでカードファイル
- 複数デバイス間では同期されない（例：PCとスマホで同じ日にアクセスすると、片方では「回答済み」表示が出ない）。これは許容する。デバイスをまたいだ同期が必要になったら、Cloudflare KV等の共有ストレージを検討する（現時点では不要と判断）

### 12.7 認証・秘密情報

| 秘密情報 | 置き場所 | 用途 |
|---|---|---|
| `ANTHROPIC_API_KEY` | Workerのsecret | 採点 |
| GitHub Fine-grained PAT（このrepoのみ、Contents: Read/Write） | Workerのsecret | カードファイルの更新 |

**ブラウザ側（index.htmlのJS）には一切の秘密情報を置かない。** 認証が必要な処理はすべてWorker側で行う。

### 12.8 v1からの変更点まとめ

| | v1 | v2 |
|---|---|---|
| 回答の入力場所 | GitHub Issueのコメント | Webサイト上のフォーム |
| 採点の呼び出し元 | GitHub Actions（issue_commentイベント） | サーバーレス関数（フォームPOST） |
| 結果の表示場所 | Issueへの返信コメント | 同じWebページ上 |
| 「どの問いへの回答か」の紐付け | Issue本文の隠しメタデータ＋`A1.`等の手動採番（取り違えが起きた） | フォーム送信時にcard/qtypeを一緒に送る（取り違えが構造的に起きない） |
| GitHub Issue | 使用する | 使用しない（`grade-response.yml`・`recall`ラベルは不要になる） |
| 新たに必要なもの | なし | サーバーレス関数のホスティング先アカウント（Cloudflare Workers等）、GitHub PAT |

### 12.9 移行方針

1. v2のWorkerとフォーム付きページを別ブランチ or 別ファイルで作り、v1と並走できる状態にする
2. 数日〜1週間、v2で問題なく回答・採点・表示ができることを確認する
3. 確認できたら `daily-question.yml` からIssue作成部分（`gh issue create`）と `grade-response.yml` 一式を削除する
